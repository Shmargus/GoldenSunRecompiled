# Handoff — battle/menu stutter, 2026-08-20

Supersedes `docs/history/HANDOFF_BATTLE_COMPILE_STUTTER.md`, whose primary
suspicion (identity drift) was wrong.

## What was wrong

`gbarecomp` `59c1858` — a WIP checkpoint, marked not-a-working-state in its own
commit message — added a 128-deep dispatch recursion guard,
`kOverlayDispatchRecursionCap`, in `src/runtime/overlay_loader.cpp`.

When it tripped, `overlay_try_dispatch` returned `0`. Callers read `0` as "no
resident code for this address". The code *was* resident and byte-identical, so
the caller re-requested a compile it already had and fell to the interpreter
meanwhile.

Guest tail jumps are emitted as host calls (**CORE-01**), so tail-looping
routines hit 128 constantly. One battle: the 24-byte body at `0x03006100`
(crc `C4790BAA`) recompiled **338 times**; 2581 RAM compiles total.

## What changed

`overlay_loader.cpp`, `.h`, `runtime_arm_default_aborts.cpp`:

1. **Guard removed entirely** — `kOverlayDispatchRecursionCap`,
   `OverlayDispatchFrame`/`Ring`, `t_overlay_dispatch_ring`,
   `OverlayDispatchGuard`, `overlay_log_dispatch_recursion`, the depth check.
   Verified against `59c1858^` (`add0815`): none existed before the checkpoint,
   so this restores prior behaviour rather than inventing new behaviour.
2. **`g_runtime_image_base` save/restore around `e.fn()` KEPT**
   (`overlay_loader.cpp:1688-1691`). Same commit, but independent — it belongs
   to the relocatable-overlay feature. Deleting it with the guard crashed on
   load at `pc=0x00000000`. **Do not remove it when tidying up.**
3. **Two diagnostics left permanently on** (unconditional stderr, no flag,
   cheap enough for normal play):
   - `[ram-compile] seq= pc= crc= addr= end= len= reason=` — one line per RAM
     compile that lands.
   - `[dispatch-miss] reason=<not-healed|region-gone|content-mismatch> pc= crc=`

| | before | after |
|---|---|---|
| RAM compiles per battle | 2581 | ~195 |
| worst single body | 338x | 16x |
| depth-cap trips | 8098 | removed |

User-confirmed: repeat casts no longer lag.

## Dead ends — do not repeat

- **CpuFastSet round-up** — exonerated, tested both ways.
- **Cache key / CRC drift** — the CRC was *identical* every time.
- **Variant eviction (`kMaxVariantsPerKey`)** — the worst offender had one CRC
  ever seen at that address, under the cap of 8.
- **Cap at 512** — trips went *up*, 8098 to 9902. Depth is unbounded; no value
  works. Do not try 1024.
- **1 GB thread stack** — only delays an unbounded recursion.

repeats on the same action, which rules out one-off cold-path work.

`logs/session_20260820_110039.phase.csv`: averages guest 4765us, render 746us,
audio 9us, compile 0us; 36 frames over 20ms. **Every spike is entirely in
`guest_us`** — so not graphics, audio, or compilation.

The worst spikes in that log are *not* the reported symptom: frames 344519
(148ms) and 344595 (167ms) match single synchronous `bridge_us` values, from

pc=0x03005CD4; LR=0xB7C00000 (fallback stop)`. With no return address to stop
at, the bridge free-walks through `gf_resume_03003908`'s state machine, healing
~40 first-time PCs in one pass. All 10 worst frames are that one discovery run,
~200 frames after `savestate_loaded frame=344326`. Cold start, in a
one-minute session.

**Next step, blocked on evidence:** a multi-minute log with the same attack
repeated after warm-up. Flat `guest_us` on the repeat means cold-load only;
comparable spikes mean something re-evicts already-healed entries. Do not ship a
fix first — three fixes were shipped on reasoning alone across 2026-08-19/20 and
none moved the symptom.

**Lead:** `src/runner_main.cpp` has its own separate same-PC recursion guard
(`SELF-DISPATCH RECURSION at 0x...`, evicting `g_verified_ram_cache`), unrelated
to the cap removed here. At `0x03005EE0` one eviction produced 15 consecutive
`content-mismatch` rejections of the same crc before a real compile landed — one
cascade, not 15 events. Not counted in `events.csv`, so no per-frame signal yet.
