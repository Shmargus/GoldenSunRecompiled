# Session 2026-08-13B — battle-lag fix and guest CPU overclock

Follow-up to `docs/SESSION_2026-08-13.md`. That session left battle lag as
"cause known, fix not built." This session built and verified the fix, found
it was actually two separate causes, and shipped a second, independent feature
(guest CPU overclock) that addresses the part of the lag that isn't a bug.

## 1. Battle lag was two problems, not one

### 1a. Our compile storms (fixed)

Root cause lived in `gbarecomp/src/runtime/overlay_loader.cpp`, in the
mutable-RAM self-heal path:

- **Bad dedup identity.** `request_identity()` hashed up to a 16KB window of
  surrounding RAM instead of the actual compiled function's real extent.
  Golden Sun's sound driver constantly mutates bytes inside that window during
  battle, so the *same* blit routine's bytes hashed differently call to call.
  Dedup failed, and the same variant got sent to gcc repeatedly.
- **Warm-load race.** `warm_load_background` only makes a warm-loaded body
  visible once per frame, via `overlay_drain_ready`. A dispatch miss on a
  routine whose `.dll`/`.pic` was already sitting on disk — just not yet
  published for this frame — triggered a redundant live compile instead of
  waiting the short remainder for the warm load.

Fix: a game-thread-only map, `s_ram_extent_seen` (`overlay_loader.cpp:134`),
remembers the largest real compiled extent seen for each RAM key and narrows
the identity window to it on subsequent calls, floored at
`kMinRamIdentityWindow = 64` bytes (`overlay_loader.cpp:142`) with a
full-snapshot fallback on first sighting of a key. Second, a targeted
synchronous warm-lookup for just the missed key runs while the background warm
load is in flight, so a miss no longer forces a live gcc compile when the
compiled body already exists on disk.

**Verification:** `ctest` 19/19, `python -m unittest discover -s tests -p
"test_*.py"` 86/86.

**Measured before/after**, same play route, sessions
`session_20260813_195708` (before) → `session_20260813_212941` (after):

| metric | before | after |
|---|---|---|
| interpreted_insns | 870,336 | 34,221 |
| ram_crc_mismatches | 1,587 | 82 |
| relocatable_alias hits/misses | 0 / 41 | 241 / 6 |
| dominant miss PC 0x03006320 occurrences | 393 | 0 |
| worst single frame | 136.8ms (6-frame compile storm) | 49.8ms one-time first-touch, no storm |

What it means for the game: the stutter that used to hit repeatedly through a
battle as the game generated new sprite-blit variants is gone. There's still
one small hitch the first time a brand-new variant shows up (49.8ms, one
frame), but it no longer chains into a multi-frame storm.

### 1b. The real GBA's own slowdown (addressed by overclock, not a "fix")

Once the compile storms were gone, some CPU-bound heaviness in battle VFX
remained — because the *original* GBA hardware is genuinely CPU-bound in those
same moments. That isn't a defect in this port; it's Golden Sun running at its
native 1x speed. See section 2.

## 2. Guest CPU overclock — shipped, user-confirmed

Full technical writeup lives in `docs/CODEX_HANDOFF.md` under "Guest CPU
overclock." Summary for this session log:

- `gbarecomp/src/runtime/runtime_bus_bridge.cpp` splits `runtime_tick` into
  `runtime_tick_common` (shared body), `runtime_tick` (the scaling door used
  by all generated code, bridge, and interpreter call sites), and
  `runtime_tick_realtime` (unscaled — used only by `pump_idle` at
  `runtime.cpp:1463-1466`).
- Halt/idle time is real elapsed hardware time and is never scaled.
  Instruction-execution cost is CPU work and is the only thing scaled.
  `drain_dma_steal` and `kIrqWakeDelayCycles` add directly to
  `g_runtime_cycles`, bypassing the scaling door entirely, so DMA-steal and
  IRQ-wake timing are unaffected regardless of factor.
- Exact integer carry accumulator, no drift. Factor is a relaxed
  `std::atomic<unsigned>`, seeded from `GBARECOMP_CPU_OVERCLOCK`, live-settable
  from the Enhancements-tab combo (`host_config_ui.cpp:309-312`), persisted as
  `CpuOverclock=` under `[Enhancements]` in the config file
  (`host_window.cpp:1311-1318,1785-1797`). A factor change resets the carry to
  0 — bounded, one-time loss of at most a few unscaled cycles.
- **1x verified bit-exact**: 8,388,608 fingerprint records compared on all 20
  fields (cycles, pc, cpsr, r0-r15) between pre- and post-change builds, zero
  differences.
- **User play-tested 2x and 4x**: battle VFX smooth, no music or animation
  problems reported. 8x deliberately not tried this session.

**Rule for future work:** any edit that touches `runtime_tick` or its call
sites must re-run the full 20-field fingerprint comparison at 1x before being
trusted as a no-op. The shipped `fp_pair_diff.py` comparator is not sufficient
by itself — see gotcha below.

## 3. Verification gotchas found this session

- **`gbarecomp/oracle/fp_pair_diff.py` checks less than its docstring claims.**
  The docstring says each record is `(cycles, pc, cpsr, r[0..15])`. The actual
  comparison in `main()` only checks `a[i][0]` (cycles) and `a[i][1]` (pc) —
  cpsr and the 16 registers are parsed out of the record but never compared.
  Anyone using this script alone to certify bit-exactness would miss a
  register- or flag-only divergence. Use a full 20-field comparator for any
  claim like "1x is a bit-exact no-op."
- **Pre-existing 1-cycle nondeterminism, unexplained.** Comparing two runs of
  the identical, unmodified binary, fingerprint-ring index 7253085
  (pc 0x08079090) differed by exactly 1 cycle between the runs; PC and all
  registers matched at that index. Root cause not identified this session.
  Practical consequence: always run an A/A control (same binary, same inputs,
  twice, diffed against itself) before concluding an observed 1-cycle (or
  similarly tiny) difference is a regression from a code change — it might just
  be this.

## 4. Negative / inconclusive results

- **Headless battle-VFX probing via scripted input did not work.** The first
  attempt to instrument a battle with `RUN BATTLE PROBE.ps1` against a battle
  savestate with no subsequent input produced `frames_presented=0` and only 4
  bridged PCs. A battle savestate sitting with no input just idles at a menu —
  it does not advance into the CPU-heavy VFX the investigation cares about.
  Scripted-input probing of battle VFX specifically has not yet been made to
  work.
- **The 2x throughput gain could not be measured, only observed.** No
  available savestate captures a moment that is actually CPU-bound (the
  battle-lag investigation's own evidence base is built around gcc compile
  storms, not steady-state CPU load). Without a mid-summon or similarly
  CPU-heavy savestate, there is nothing to point a frame-time probe at that
  would show the scaling effect numerically. The 2x/4x results reported above
  are the user's direct play-test judgement, not an instrumented number.

**Remaining evidence gap:** a savestate captured mid-summon (or at another
moment known to be genuinely CPU-bound on real hardware) is needed before the
overclock's throughput benefit can be measured with a probe instead of taken
on the user's word. Until such a savestate exists, do not upgrade the "user
confirmed smooth at 2x/4x" claim to an instrumented number.
