# Session 2026-08-13 — measurement session

Read this before acting on `TECHNICAL_HANDOFF.md`'s "NEXT STEP" section. That
section is wrong and is corrected below.

## The previous handoff's named next step is dead

`TECHNICAL_HANDOFF.md` named the halt/idle pump loop (74.6% of headless wall)
as THE next step, on the belief that it "advances in small chunks rather than
jumping directly to the next scheduled event."

That belief is false. `pump_idle` (`gbarecomp/src/runtime/runtime.cpp:1426`)
already advances to the next device event:
`min(ppu.cycles_until_next_event, io.cycles_until_next_timer_event,
audio.cycles_until_next_sample)`, capped by the remaining frame budget.
`runtime_tick` then recomputes the same horizon internally via
`recompute_event_budget`. The ~790 iterations per halt are the real
device-event count per frame, not an artificial chunking artifact.

**Do not implement "skip straight to the next event." It is worth ~1%.**

## What the halt bucket actually is

Measured, 1800 headless frames, `build/gs011/cost_probe.ps1` methodology
(1 discarded warmup + 5 measured runs). Probe-on wall carries ~20.7% overhead;
off-probe wall ≈ 6518ms.

| bucket | ms | share of halt |
|---|---|---|
| guest VBlank ISR via `runtime_irq()` | 3073 | 52% (1.714ms × 1,793 IRQs) |
| PPU scanline render | 2021 | 34% (288,008 scanlines) |
| CRC32 revalidation (`heal_entry_crc_ok`) | 246 | 8% |
| loop + horizon recompute overhead | ~59 | ~1% |

`tick_devices` and `irq_handler` overlap; containers do not sum to 100%.

## Ruled out this session, with evidence

- **Interpreter involvement in the ISR.** `interpreted_insns=0`,
  `dispatch_misses=0`, `bridge_us_sum=0` across 5 runs. The ISR is 100%
  natively dispatched. A hypothesis that the ISR was secretly interpreting was
  tested and disproved.
- **The halt loop's iteration count** (see above).
- **CRC32 revalidation as the dominant cost.** Priced at 246.4ms / 8%.
  `heal_entry_crc_ok` (`gbarecomp/src/runtime/overlay_loader.cpp:296`) hashes
  the whole function body on every call; 215 healed RAM functions, mean 32.4
  bytes, 160ns and 44.9 bytes per call. Real but minor. Do not weaken this
  check — its safety rationale is a planner call.

## Open lead: per-instruction bookkeeping in recompiled code

Residual ≈ 2827ms sits inside the recompiled function bodies. Healed RAM
functions average ~11 guest instructions per call, giving roughly **167ns per
guest instruction** — interpreter-grade, not native-grade. The generator emits
an out-of-line `runtime_tick()` call per guest instruction (~65M calls per 1800
frames) plus `runtime_mem_cycles`.

Measured call volumes, 1800 frames: **`runtime_tick` = 64,733,186 calls**,
**`runtime_mem_cycles` = 112,831,449 calls** (more, because LDM/STM sum several
`runtime_mem_cycles` results into one `runtime_tick(cyc)` — the
`cyc += runtime_mem_cycles(...)` pattern in
`gbarecomp/src/armv4t/arm_codegen.cpp`). If the 2827ms residual were entirely
these, that is ~43.7ns per `runtime_tick` call, or ~15.9ns per call combined.

**The calls are genuinely out-of-line**, confirmed from the shipping binary:
`objdump -dr` on `recompiled_000.cpp.obj` shows real `call` instructions with
`IMAGE_REL_AMD64_REL32 runtime_tick` relocations — 7,893 of them in that one
object file. `build/gs011`'s `CMakeCache.txt` has
`CMAKE_INTERPROCEDURAL_OPTIMIZATION=OFF`, so there is no LTO to inline them.

**The A/B experiment did NOT complete. The hypothesis is unproven — do not
treat it as established.** The inline-fast-path variant was not attempted in
code: it would require exposing `g_active_bus` / `g_active_ppu` /
`g_pending_cycles` / `g_event_budget` (currently file-static in
`runtime_bus_bridge.cpp`), and partially duplicating the
`drain_dma_steal`/IRQ-pending check risked altering IRQ-delivery timing. A
whole-build LTO proxy was substituted instead and never finished linking.

**LTO may not be viable on this machine at all.** Both
`build/gs011_lto_probe/GoldenSunRecomp.exe` (00:44) and
`build/gs011_tickprobe/GoldenSunRecomp.exe` are 0 bytes. Mid-link observation
showed GCC `-flto=auto` WPA `lto1` peaking near 3.2GB RSS followed by ~16
parallel LTRANS workers at ~450-480MB each, with free memory dropping to
~1.2GB on a 16.7GB machine. Consistent with memory pressure, but **no captured
stderr proves the cause** — get the actual link error before concluding.

**Cleanup owed:** `gbarecomp/src/runtime/runtime_bus_bridge.cpp` carries an
uncommitted throwaway counter (`g_cost_mem_cycles_total_calls`); revert or
keep it deliberately before any commit. `build/gs011_tickprobe` holds stale
0-byte link artifacts.

## Battle lag — cause identified, fix direction clear

`BATTLE SLOW.txt` and a later session log show Golden Sun generating sprite-blit
code into IWRAM at runtime, 44 distinct PCs in 0x03006000..0x0300645C reporting
"DYNAMIC RAM CODE ... no registered identity matches the live bytes".

Self-heal *is* attempted for these (fixed identity → PIC/content-hash identity →
CRC-keyed overlay cache → interpret + enqueue compile). The lag is gcc
compiling blit variants **mid-battle**.

Two facts that shape the fix:

1. **The variant set is bounded and converges.** Warm-loaded RAM overlays grew
   415 → 462 → 499 → 513 across sessions; the cache now holds 1836 files. In the
   latest session, 40 dynamic-RAM-code hits produced only **4** fresh heals —
   the rest were served from cache. The user reports battle performance is now
   good. (Caveat: that is one session and a subjective judgement, not a
   stopwatch measurement.)
2. **The same code is relocated to different addresses.** Identical CRCs appear
   at multiple PCs — e.g. `17B82AA7` at 0x03007B10/B24/B28/BC0/BFC and
   `3B88AD7A` at 0x03007AC0/B6C/BEC/BF8. Address-keyed lookup misses on
   relocation. The repo already has `*_relocatable` (position-independent)
   identities; leaning on content-keyed lookup should shrink the variant set
   further.

**Candidate fix:** ship or pre-warm the cache so a first-time player never pays
the mid-battle compile storm, plus content-keyed (address-independent) lookup.
The in-memory half is now implemented safely: upstream ABI v5 emits mutable-RAM
heals position-independently and reuses a completed body at another address only
after mode, extent, CRC, and exact bytes match. Old ABI v4 cache entries rebuild
once. Known slots 1..7 were prewarmed. New ABI-v5 RAM compiles persist an
atomic, schema-gated local `.pic` sidecar with exact function bytes, so safe
cross-address reuse now survives restart. Malformed metadata is ignored and
cache bytes must never leave the ignored local cache.

An instrumented probe exists: `GSR_DYNAMIC_RAM_PROBE=1` /
`GSR_DYNAMIC_RAM_PROBE_WINDOW=<bytes>` in `src/runner_main.cpp`, built in
`build/gs_probe`, driven by `RUN BATTLE PROBE.ps1`. It prints a per-PC table
(distinct hashes, executions, overlay hits, interpreted insns, ms) to stderr at
exit. **Never yet run through an actual battle** — that table is still the
missing hard evidence for distinct-variant counts.

## Open: world-map visual artifact

Horizontal streaking across the top band (the sea) on the world map.

**Repro: savestate slot 6 is the world map** showing the artifact (slot 7 is a
battle). Reproduces headlessly:
`build/gs011/GoldenSunRecomp.exe --load-state ... --frames N --dump-png` with
the five launcher env vars. Repeat runs are byte-identical.

**The artifact alternates on an exact 2-frame period** — frames 1/3/5 clean,
frames 2/4/6 streaked. That rules out a fixed per-scanline off-by-one, which
would appear every frame.

**The obvious batching hypothesis is refuted.** Normal lazy catch-up cannot
span a scanline boundary: `recompute_event_budget` takes
`min(..., ppu->cycles_until_next_event())`, and `cycles_until_next_event()`
(`gba_ppu.cpp:171-179`) always stops at the next dot boundary. HBlank-timed DMA
(`run_timed_dma(2)`, `gba_io.cpp:305`) runs inside `tick_devices`'s per-event
loop right after `render_scanline` for that same event
(`runtime_bus_bridge.cpp:793-816`) — correctly ordered per scanline even in a
large batch. So HBlank-**DMA**-driven effects are provably immune.

**The one real ordering gap found:** `drain_dma_steal`
(`runtime_bus_bridge.cpp:899-926`) can hand `tick_devices` a multi-scanline
cycle count, since a transfer's stolen-cycle cost scales with word count
(`dma_transfer_cost`, `gba_io.cpp:180-191`) and a few-hundred-word transfer
exceeds one scanline's 1232 cycles. Several scanlines would then render with
stale registers, with any HBlank-**IRQ**-driven write deferred until after all
of them. HBlank/VBlank/VCount IRQs only set IF inside `tick_devices`; the ISR
runs later back in `runtime_tick` (`runtime_bus_bridge.cpp:1008+`).

**Measured negative result:** the `drain_dma_steal` theory is killed. Across six
post-load frames there were 1,155 steals; the global maximum was 1,026 cycles,
the active-display maximum was 514 cycles, and no steal reached the 1,232-cycle
scanline length. Clean and streaked frames therefore had no qualifying steal.

The earlier absolute probe bracket was stale: headless savestate loading resets
`g_runtime_cycles` to zero (`runtime.cpp:1613-1624`). The correct six-frame
window was `GBARECOMP_CYC_LO=0`, `GBARECOMP_CYC_HI=1685376`.

**Root cause fixed upstream.** The MMIO and IRQ rings proved the effect uses
DMA0 HBlank repeat, not HBlank/VCount IRQ. Each VBlank the game alternates two
affine tables; the artifact table contains nonzero vertical affine terms in the
affected top rows. The old PPU renderer used the DMA-written per-line reference
and then added the absolute scanline's vertical term again.

`gbarecomp` now models the GBA's hidden BG2/BG3 affine references: BGxX/Y writes
reload them, each visible line advances them once, and VBlank reloads them.
Synthetic HBlank-reload and save-state roundtrip tests cover the behavior. An
optional `AFRF` snapshot section preserves the hidden state without invalidating
older slot files. Slot 6 frames 1-6 are clean and repeat deterministically; PPU,
DMA, bus, frame-timing, and all 86 public Python tests pass.
