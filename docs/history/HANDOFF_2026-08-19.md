## 1. Walk Speed QoL option — built, does not work (start here)

The user tested twice; the multiplier has no visible effect in game.

What exists now:

- F1 → Enhancements → **QoL → Walk Speed** (1x/2x/3x/4x, default 1x), persisted
  as `WalkSpeed=` in the `[Enhancements]` section of `config.ini`
  (`gbarecomp/src/runtime/host_config_ui.cpp:406-415`,
  `host_window.cpp:1663-1704,2193-2260,2691-2701`).
- The scale itself: `runtime_trace_event` arms a pending-override slot
  (`gbarecomp/src/armv4t/runtime_arm.cpp:322-341`) which `bus_write_u32`
  consumes (`gbarecomp/src/armv4t/runtime_arm.h:349-356`), for guest pc
  `0x0800DC7A` writing `0x0203155C`, replacing the stored total with
  `old + N * (new - old)`.

Why that target: measured live, the player's movement accumulator is
`0x0203155C`; `0x0800DC7A` (`str r3,[r4,#0x10]`) is its only per-frame writer
while moving, and `r3 = old + increment`. There is **no writable speed field** —
the increment comes from an easing subroutine reached through a function-pointer
trampoline, so scaling the write is the only available lever. Holding B (run) is
~1.45x and goes through the same accumulator.

**Next step — stop guessing, instrument it.** Two builds have now been shipped
on reasoning alone and both failed. Add a temporary one-shot stderr print (to be
removed afterwards) answering, in order:

1. Does `gsr_walk_speed_multiplier()` actually return 2/4 in the running game
   after the menu selection, or is the menu writing somewhere the runtime never
   reads? (Suspect first — it is the cheapest to disprove.)
2. Does the hook condition ever match at runtime — i.e. does a write to
   `0x0203155C` from pc `0x0800DC7A` occur at all in `build/gs011_opt`? All the
   address measurements were taken on `build/gs011_rel`. If `gs011_opt` reaches
   that code through a different tier (healed overlay, interpreter, a different
   generated body), the pc seen by the hook may differ or the store may not go
   through `bus_write_u32` at all.
3. If it matches, does the override survive to memory — read `0x0203155C` back
   immediately after and compare with what was intended.

Answer those three before touching the design again.

Also worth reconsidering: even if it lands, scaling this accumulator may fight
the game's own easing curve. A cleaner alternative, if instrumentation shows the
hook is fine but motion is not, is to make the game believe B is held (run) and
scale from there.

## 2. Text speed QoL option — not started, one route left

The game's own Slow/Normal/Fast setting exists (Start → Change settings →
"Message speed") and is reachable headlessly. Its RAM mirror was **not** found:
diffing EWRAM and IWRAM across the three states drowns in per-frame RNG churn

`0x0200046C` is wrong.

Next route: breakpoint the code that READS the setting — during text reveal, or
during the settings screen's redraw when the value changes — instead of more
value diffing. Glyphs are not drawn via the BG0-3 tilemap, so look at OBJ/sprite
paths.

## 3. Mercury Lighthouse crash — parked, cause narrowed

Reproducible from savestate 5 via the launcher; aborts with `interpreter
Undefined at pc=0x030020A8`. The word there is data, so adding an interpreter
lowering would be wrong.

Established: the savestate loads correctly; DMA refills the shared code slot at
`0x03002000` with correct code right before use (frames 2295/2569/2570); then
the guest's own unpacker writes **32 zero bytes** over `0x03002000-0x0300201F`
and correct data from `0x03002020` on; the guest then legitimately returns into
`0x03002000` and runs the zero prefix into data. Our runtime substitutes
nothing. Ruled out: savestate load, stale host buffers, baked literals,
`RamOverlayRegistry` (dead code), BIOS HLE copies, DMA repeat handling,
mid-body mis-healing.

Open question: where the unpacker's destination pointer comes from — it may be
writing 0x20 bytes too low. That is the next trace.
